    Лабораторная работа 3

    Упаковка FastAPI приложения в Docker, работа с источниками данных и очереди

    Цель работы

    Научиться упаковывать FastAPI приложение в Docker, интегрировать парсер данных с базой данных и вызывать парсер через API синхронно и через очередь задач асинхронно.

    Что было сделано

    Разработана микросервисная система из 5 контейнеров, объединенных через Docker Compose. За основу взяты FastAPI-приложение из лабораторной работы №1 (модели данных, подключение к PostgreSQL) и парсер цитат с сайта quotes.toscrape.com из лабораторной работы №2.

    Подзадача 1 — Упаковка в Docker

    Что такое Docker и зачем он нужен

    Docker — платформа для запуска приложений в изолированных контейнерах. Контейнер упаковывает в себя приложение и все его зависимости: интерпретатор Python, библиотеки, переменные окружения. Это решает проблему «у меня работает, а у тебя нет» — контейнер одинаково запускается на любой машине, поддерживающей Docker.

    Dockerfile

    Для каждого сервиса написан свой Dockerfile — инструкция по сборке образа:

    FROM python:3.11-slim       # базовый образ с Python
WORKDIR /app                # рабочая директория внутри контейнера
COPY requirements.txt .     # копируем зависимости отдельно (для кэширования)
RUN pip install --no-cache-dir -r requirements.txt  # устанавливаем библиотеки
COPY . .                    # копируем исходный код
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

    Зависимости копируются и устанавливаются отдельно от кода намеренно: Docker кэширует слои образа. Если изменился только код, Docker не будет переустанавливать все библиотеки — возьмет из кэша, что значительно ускоряет пересборку.

    Docker Compose

    Docker Compose позволяет описать и запустить несколько контейнеров одной командой. В docker-compose.yml описаны 5 сервисов:

    Сервис Образ / Сборка Порт Назначение
    db postgres:16-alpine 5432 База данных PostgreSQL
    redis redis:7-alpine 6379 Брокер сообщений для Celery
    parser ./parser_service 8001 Сервис парсинга HTML
    api ./api_service 8000 Основное FastAPI приложение
    celery_worker ./api_service — Воркер очереди задач

    Все сервисы находятся в одной Docker-сети и обращаются друг к другу по именам: http://parser:8001, redis://redis:6379, @db:5432.

    Для db и redis настроены healthcheck — проверки готовности. Сервис api не стартует раньше, чем база данных и Redis пройдут эти проверки. Это исключает ошибки при старте из-за гонки между сервисами.

    Подзадача 2 — Вызов парсера из FastAPI (синхронный подход)

    Сервис парсера (parser_service)

    Парсер из лабораторной работы №2 был обернут в отдельное FastAPI приложение с одним эндпоинтом:

    POST /parse
Body: {"url": "https://quotes.toscrape.com/"}

    Сервис получает URL, загружает страницу через requests, парсит HTML с помощью BeautifulSoup, извлекает текст цитат, авторов и теги, и возвращает результат в виде JSON.

    Эндпоинт синхронного парсинга в основном API

    Подзадача 3 — Вызов парсера через очередь (асинхронный подход)

    Что такое Celery и Redis

    Redis — хранилище данных в памяти. В данной работе используется как брокер сообщений: хранит очередь задач, которые нужно выполнить.

    Celery — система асинхронной обработки задач. Состоит из двух частей: - Producer — код в api_service, который кладет задачи в очередь - Worker — отдельный процесс (celery_worker), который забирает задачи из очереди и выполняет их

    Конфигурация Celery

    Создан файл celery_app.py с объектом Celery, подключенным к Redis как брокеру и бэкенду результатов:

    celery_app = Celery(
    "lab3",
    broker="redis://redis:6379/0",   # куда класть задачи
    backend="redis://redis:6379/0",  # куда сохранять результаты
    include=["tasks"],               # где искать задачи
)

    Разница между синхронным и асинхронным подходом

    Синхронный подход (POST /parser/parse)

    Клиент отправляет запрос и блокируется — ждет пока сервер выполнит всю работу целиком.

    Время:  0ms        500ms      1200ms    1500ms
         |          |           |         |
Клиент: [запрос]──────────────────────[ответ]
API:             [ждет парсер][сохр. в БД]
Парсер:          [загрузка страницы][парсинг]

    Плюсы: - Простота — клиент сразу получает результат - Не нужны дополнительные запросы для получения данных

    Минусы: - Клиент заблокирован на все время выполнения - Если парсинг длится 30 секунд — соединение держится 30 секунд - При большой нагрузке быстро кончаются рабочие потоки сервера - Если соединение оборвется — результат потеряется

    Асинхронный подход (POST /parser/parse/async)

    Клиент отправляет запрос, получает task_id немедленно и сам опрашивает статус когда нужно.

    Время:  0ms   50ms         1500ms
         |     |              |
Клиент: [запрос][task_id]    [GET /status] → SUCCESS
API:           [в Redis]
Worker:              [берет задачу][парсит][сохраняет]

    Плюсы: - Клиент не блокируется - Сервер может обрабатывать другие запросы пока воркер работает - Задачи не теряются при разрыве соединения — они уже в очереди - Можно масштабировать: добавить больше воркеров не меняя API - Воркер автоматически повторяет задачу при ошибке

    Минусы: - Сложнее в реализации - Клиент должен делать дополнительные запросы для получения результата - Нужна дополнительная инфраструктура (Redis, Celery)

    Когда что использовать

    Ситуация Подход
    Операция занимает < 1-2 секунды Синхронный
    Операция долгая (парсинг, генерация, обработка файлов) Асинхронный
    Важно сразу вернуть результат пользователю Синхронный
    Пользователь может подождать или получить уведомление позже Асинхронный
    Нужна надежность (повторные попытки при ошибке) Асинхронный
    Высокая нагрузка, много одновременных запросов Асинхронный

    Запуск проекта

    # Собрать и запустить все контейнеры
docker-compose up --build

# Запустить в фоне
docker-compose up --build -d

# Остановить
docker-compose down

# Остановить и удалить данные БД
docker-compose down -v

    После запуска доступны: - Основное API и документация: http://localhost:8000/docs - Сервис парсера и документация: http://localhost:8001/docs

    Выводы

    В ходе лабораторной работы была разработана микросервисная система, в которой каждый компонент изолирован в отдельный Docker-контейнер со своими зависимостями. Реализованы оба подхода к вызову парсера: синхронный, при котором клиент ожидает результата напрямую, и асинхронный через очередь Celery и Redis, при котором клиент получает ответ немедленно, а задача выполняется в фоновом процессе.

    Асинхронный подход особенно важен для операций, которые занимают значительное время — таких как парсинг веб-страниц, обработка файлов или вызов внешних API. Он позволяет не блокировать пользователя, масштабировать обработку через добавление воркеров и обеспечивать надежность через механизм повторных попыток.
